## Описание проекта

Приложение `shop` построено по схеме **MVC** (в терминах Django — MTV):

| Компонент MVC | Реализация |
|---------------|------------|
| **Model** | `shop/models.py`: `Product`, `PromoCode`, `Purchase`, функция `apply_discount` |
| **View** (представление) | шаблоны `shop/templates/shop/{base,index,purchase_form}.html` |
| **Controller** | `shop/views.py` (`index`, `PurchaseCreate`), `shop/forms.py` (`PurchaseForm`), маршруты `shop/urls.py` |

### Доработка по варианту 1

- **`PromoCode`** — промокод (`code`, `discount` ∈ {5, 10, 15} %, `is_active`). Код
  хранится в верхнем регистре; поиск `PromoCode.find_active()` не зависит от регистра и
  пробелов и находит только активные коды.
- **`apply_discount(price, percent)`** — цена со скидкой, округление до рубля
  (0,5 — вверх, `Decimal` + `ROUND_HALF_UP`), проверка входных данных.
- **`Purchase`** хранит примененный промокод и **итоговую цену**, которая фиксируется в
  момент покупки (последующее изменение цены товара или удаление промокода ее не меняет).
- **Главная страница**: поле ввода промокода (`/?promo=TOY10`); при верном коде показываются
  старая (зачеркнутая) и новая цены, при неверном — сообщение об ошибке. Ссылки «Купить»
  передают промокод на страницу покупки.
- **Страница покупки**: поле «Промокод» (предзаполняется из ссылки), валидация в
  `PurchaseForm.clean_promo`; после покупки выводится сумма к оплате.
- **Админка**: зарегистрированы все модели, цена покупки — только для чтения.
- **Фикстура** `products.yaml`: 5 игрушек и промокоды `TOY5`, `TOY10`, `TOY15`
  (+ неактивный `SUMMER2021` для проверки).
- Новый внешний вид страниц: общий шаблон `base.html` со стилями.

### Прочие изменения исходного проекта

- БД настраивается через `DATABASE_URL` (`dj-database-url`); по умолчанию — SQLite,
  чтобы проект запускался без установки сервера. PostgreSQL проверен (см. ниже).
- `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS` берутся из переменных окружения.
- Исправлено имя `shop/tests/__init.py__` → `__init__.py`.
- Зависимости обновлены до актуальных (Django ≥ 5.2, psycopg 3).

## Запуск

```bash

pip install -r requirements.txt

```


## Выводы

1. Модель MVC разделяет данные и бизнес-логику (модели), отображение (шаблоны) и
   обработку запросов (контроллеры). Благодаря этому функциональность промокодов
   добавлена в основном в модель (`PromoCode`, `apply_discount`, расчет цены в
   `Purchase`), а контроллеры и шаблоны лишь используют ее.
2. Django берет на себя рутину: ORM и миграции (схема БД обновлена одной командой
   `makemigrations`), фикстуры для начальных данных, валидацию форм, админ-панель.
   Перенос БД с PostgreSQL на SQLite и обратно не потребовал изменения кода.
3. Вынос расчета скидки в чистую функцию позволил тестировать ее без БД и веб-сервера;
   хранение итоговой цены в покупке защищает историю заказов от изменения цен.
4. 74 модульных теста покрывают 100 % операторов и ветвлений приложения. Тесты
   нашли бы типичные ошибки: неверное округление, чувствительность к регистру
   промокода, применение неактивного кода, потерю промокода при повторной отрисовке
   формы.
5. Сервисы, на которых строился CI/CD в методичке (Travis CI, Heroku), стали платными /
   недоступными — инструменты CI/CD быстро меняются, поэтому важны общие принципы
   (автоматический прогон тестов и развертывание при каждом изменении), а не конкретный
   сервис.

## Ответы на контрольные вопросы (кратко)

**ЛР 2**

1. **MVC** (Model–View–Controller) — архитектурный шаблон: *модель* хранит данные и
   бизнес-логику, *представление* отображает данные, *контроллер* принимает ввод
   пользователя, обращается к модели и выбирает представление. Жизненный цикл: запрос →
   маршрутизатор → контроллер → модель (чтение/изменение данных) → контроллер передает
   данные в представление → ответ клиенту.
2. Фреймворки: Django (Python, MTV), Ruby on Rails, ASP.NET Core MVC, Spring MVC (Java),
   Laravel и Symfony (PHP), Express + шаблонизаторы (Node.js), Phoenix (Elixir).
3. **Автоматическое развертывание в CI/CD**: каждое изменение в репозитории запускает
   конвейер — сборка, тесты, при успехе — публикация артефакта и выкладка на сервер
   (Continuous Delivery — с ручным подтверждением, Continuous Deployment — полностью
   автоматически). Секреты (ключи API) хранятся зашифрованными, конфигурация задается
   переменными окружения, конвейер описывается кодом (`.github/workflows/*.yml`,
   `.gitlab-ci.yml` и т. п.).

**ЛР 3**

- **Модульный тест** проверяет отдельную единицу кода (функцию, класс, метод)
  изолированно от остальных. Структура: Arrange (подготовка, `setUp`, фикстуры) → Act
  (вызов) → Assert (проверка).
- В Django `SimpleTestCase` не использует БД, `TestCase` оборачивает каждый тест в
  транзакцию с откатом, `Client` эмулирует HTTP-запросы, `subTest` позволяет проверять
  набор входных данных в одном тесте.
- **Покрытие кода** (coverage) показывает, какие операторы и ветвления выполнялись при
  тестах; 100 % покрытие не гарантирует отсутствия ошибок, но показывает непроверенные
  участки.
